## P5 — Diagnose the proof-approval crash (blocked on owner input)

**Symptom:** on the coupon calculator, approving a proof made the entire
calculator disappear.

**Already done:** ErrorBoundary + DOM guard ported to all eight calculators
(`e5b4c5f`), so the blank page becomes a reload prompt plus a console trace.
That is mitigation, **not the fix** — the underlying throw is unidentified.

**Not reproducible with synthetic input:** the full upload → proof → approve
flow was driven in headless Chromium with PNG artwork and completed cleanly.
The owner's case used a real multi-page PDF with an orientation mismatch and
a blank page inserted, which exercises the print-ready PDF generation path
(jsPDF + pdf.js) that the PNG path skips.

**What you need from the owner** — ask for this explicitly in chat:
1. Reproduce once with the browser console open (F12 → Console) and paste the
   red error, including the line beginning
   `[PPS calc] render error caught by ErrorBoundary:`.
2. The PDF itself, if they can share it.

**Where to look once you have it:** the approve handler is try/caught and
alerts on failure, so the throw is in **render** after `setArtApproved(true)`
/ `setApprovalPkg(pkg)`. Prime suspect is the post-approval download block
(`approvalPkg && (artApproved || debug) && (() => {…})()`), which calls
`approvalPkg.previewBlobs.filter(...)` at render time while the handler only
validates `manifestBlob`. `generateApprovalPackage()` has a single return
that always includes `previewBlobs`, so a partial/exotic return shape or a
different field being undefined is the thing to prove.

## P6 — Presets admin patch (repo-only, fold into the next deploy)

Two code fixes committed **after** the `e5b4c5f` pin. Do **not** deploy
separately — fold into whatever ships next, and update P2's pinned SHA and
byte counts when you do.

**Commit `ff542a1`** — `pps-calculators.php` + `pps-presets-admin.php`:

1. **`pps_sanitize_defaults_blob()` no longer lowercases keys.** It ran
   `sanitize_key()` over the defaults **keys**, so every camelCase field saved
   through the Presets admin form was stored dead — `sizeLabel` →
   `sizelabel`, `insidePaperType` → `insidepapertype`. The calculator reads
   `PPS_CONFIG.defaults` by exact key, so such a preset rendered an **empty
   form with no error** in the admin, the console, or the page source. Keys
   are now charset-restricted `[A-Za-z0-9_-]` with case preserved; a key that
   sanitises to empty is dropped rather than stored under `''`.
2. **Admin defaults placeholder corrected.** It suggested
   `{"qty": 250, "pages": 16, "size": "5.5x8.5"}` — wrong field (`size` vs
   `sizeLabel`) and wrong value (lowercase `x` vs U+00D7 `×`), so it actively
   taught the broken form.

**No data repair needed.** `letterhead` is the only existing row and it was
written straight to the option, so it kept its camelCase.

**This is a hard prerequisite for creating any preset through the admin
form** — see `docs/PRESET_CANDIDATES_REVIEW.md`. Do not let anyone build the
SEO preset set until this is on the target site.
