**This is a verification-and-gaps brief, not a deploy plan.** Every check below
was run against the live sites on 2026-08-14 ~22:40 UTC before a word of it was
written.

   the eight compiled calculators 11:08:05–11:08:44. Verified byte-for-byte

### The binder-throat knob was half-wired — the sharpest edge of the split

This branch's calculators (source **and** the `dist/` live on production)
**read** `perfectbound_binder_throat_in`, with an embedded fallback of `13`.
This branch's `pps-config-admin.php` never declared it. Only theirs did.

- On **production** this was never broken: their config-admin declared it, the
  calculator read 13, and the operator could see and edit "Perfect Binder Throat".
- **Pricing was not at risk from a wrong deploy today** — both the embedded
  fallback and the declared default are `13`, so swapping in this branch's
  config-admin would have changed no number.
- **It would have become a pricing risk the moment anyone tuned that knob.** A
  tuned value lives in `pps_calc_config`; if the admin file that declares the key
  were replaced by one that doesn't, the key stops being injected and every
  perfect-bound and coupon quote silently reverts to 13″ — a money regression
  with no error and no log line.

**Closed in `60d4022`.** The knob is now declared in `pps-config-admin.php`
(line 133, default 13) with its Central Config label row (line 1436) and read by
both `calc-perfect-bound.html` and `calc-coupon-book.html`. End to end on one
branch.

### How the split was resolved

The four files were adopted onto `claude/optimistic-wozniak-11ql3y` — but only
after proving the adoption could not lose work, because two of them **had**
changed on this side since the divergence (`pps-presets-admin.php` ×2 commits,
`pps-config-admin.php` ×5).

| File | Test | Result |
|---|---|---|
| `pps-presets-admin.php` | 3-way merge, base `28f2b16` | **Clean, and byte-identical to theirs (56,995).** Their copy already contains every change on this side — `365c7df` had aligned to production, which carried `ff542a1` and `8134a06`. |
| `pps-config-admin.php` | 3-way merge + `--numstat` | **Clean, byte-identical (111,697); 2 insertions, 0 deletions.** Strict superset of this branch's copy. |
| `pps-imposition.php` | blob compare vs base | Untouched on this side since divergence — fast-forward, nothing to lose. |
| `imposition-tool.html` | blob compare vs base | Same. |

**The parity invariant was checked, not assumed.** CLAUDE.md requires
`flatGrid` / `flatImp` / `stickerImp` in the imposition tool to stay verbatim
ports of the calculators' imp functions, and production runs *this* branch's
calculators against *their* imposition tool. Diffing all six flat/booklet
calculators from `28f2b16` to `f945ada` shows **zero** imp-related changes, so
the ported copies remain in step.

All three PHP files pass `php -l`. Verified after adoption: 21/21 plugin files
and 8/8 calculators match the production listing captured in §2.

**Nothing needs deploying.** Production already runs these exact bytes; the repo
caught up to reality rather than proposing a change.

### What the adopted `pps-imposition.php` change actually does

Worth recording, since it arrived from the other branch rather than being
authored here. It adds a second output type alongside `IMPOSED_`: a `CLEAN_`
prefix for a 1:1 sanitized copy of the customer file with active content
stripped, safe for staff to open. The upload validator accepts both prefixes,
`pps_impose_pick_artwork()` skips `CLEAN_` files (they are outputs, not
artwork), and the order note names which of the two was filed. The +313 lines in
`imposition-tool.html` are the tool side that produces them.

**Why this matters more than it looks.** `docs/UPDATE_PIPELINE.md` Lane A is
*staging first, then the same SHA to production*. That ordering got inverted
here: production is ahead. A "clean on staging" result now tells you about code
production stopped running two days ago — and the next WooCommerce or Astra
update, which is the one thing staging genuinely exists for, would be exercised
against the wrong plugin.

### Catch-up deploy (do this before any plugin/core update)

Pull-based, pinned, `mcp_ping` after each write:

| File | SHA | Expected bytes |
|---|---|---|
| `pps-calculators.php` | `f945ada` | 322,038 |
| `pps-defaults-url.php` | `f945ada` | 9,067 |
| `pps-presets-admin.php` | `60d4022` (this branch, since §3) | 56,995 |
| `pps-config-admin.php` | same | 111,697 |
| Eight calculators | the published build | as the table in §2 |

Calculators go to `pps-calculators/_pending_html/<file>`, then `mcp_ping` to
fire the deploy hook. Do `pps-defaults-url.php` **before** `pps-calculators.php`
— the loader is `file_exists`-guarded, so the reverse order is harmless, but
this way there is never a window where the require target is missing.

Then clear WP Rocket on staging. This is the step most often skipped, and it
makes a good deploy look broken.

## Appendix — how to re-run this verification

Nothing here needs a shell on the server.

1. `pps_plugin_list_files` on `pps-calculators`, both sites. Compare sizes to
   `git cat-file -s <ref>:<file>`. A size matching **no** commit means someone
   edited in place — stop and read the file before overwriting it.
2. `pps_uploads_list_files` with `subdirectory: pps-calculators`, `order_by: size`.
   The eight `calc-*.html` entries are what is actually served; the `_pending_html`
   listing only shows what was *staged*. Fresh `js/calc-*-<hash>.js` timestamps
   after a deploy prove real traffic hit the new HTML.
3. Read one small deployed file back in full (`pps-defaults-url.php` is ideal at
   9 KB) and diff it against the repo. Byte counts can collide; content cannot.
4. `wp_get_option` on `pps_presets` to confirm the row set and that defaults keys
   kept their camelCase. **Never** read `pps_calc_config`, `pps_gdrive`,
   `woocommerce_stripe_settings` or `wp_mail_smtp` — live credentials, public repo.
